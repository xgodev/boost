# builder `@Controller` — design

Issue #109.

## Intent

Writing a Kubernetes controller should be as easy as writing a REST route on
boost. Today boost only builds a `*kubernetes.Clientset`
(`factory/contrib/k8s.io/client-go/v0`); a controller means learning
controller-runtime (manager, reconciler, work queue, predicates, finalizers),
writing the CRD and RBAC YAML by hand and wiring the main.

The maintainer wants a fifth builder door, next to `@REST`, `@GRPC`, `@MCP`
and `@Function`: the dev writes a function that reacts to something in the
cluster and annotates it; `go generate` writes the rest, and the generated
app starts, connects to the cluster and keeps watching it.

## Decided (by the maintainer)

- It is a **builder door**, generated by the same `go generate` run as the
  others.
- It watches **any resource**: built-in kinds (Deployment, Pod, ConfigMap…)
  and custom resources (CRDs). The dev declares what to react to.
- **Both styles**, event and state, because each alone has a hole (an event
  is lost while the controller is down; a state-only function never knows
  what happened).
- The reaction is declared **in the annotation**: one function per event.
- For a **new type**, `go generate` writes the CRD YAML from the dev's
  annotated Go struct, like kubebuilder's controller-gen.

## Syntax

```go
package servicefor

// New provides the handler.
// @Provide(index=0)
func New(c client.Client) *Handler { return &Handler{c: c} }

// Sync makes sure the Deployment has its Service.
// @Controller(on=sync, owns=corev1.Service, app=controller)
func (h *Handler) Sync(ctx context.Context, d *appsv1.Deployment) error { ... }

// Deleted drops the DNS record of the Deployment.
// @Controller(on=deleted, app=controller)
func (h *Handler) Deleted(ctx context.Context, d *appsv1.Deployment) error { ... }
```

| Key | Required | Meaning |
|---|---|---|
| `on` | yes | `created`, `updated`, `deleted` or `sync` |
| `owns` | no | only with `on=sync`: types the object owns, written as the file writes them (`corev1.Service`); a change to one of them runs `sync` of the owner. Repeatable as a list (`owns=[corev1.Service, corev1.ConfigMap]`) |
| `selector` | no | label selector, quoted when it has a comma (`selector="app=web,tier!=db"`); objects outside it are ignored by that function |
| `app` | no | application, default `api` |

- The handler is `func(context.Context, *T) error`, a function or a method;
  `*T` is the watched type. The kind is taken from `T` (no `kind=` key): a
  type of `k8s.io/api` or a type marked `@CRD`.
- A method needs a provided receiver, as in `@REST`.
- `@Controller` is repeatable on different functions of the same type: each
  function is one event of that type.
- Returning an error retries the same call with backoff.

### The events

| `on` | Called when | Guarantee |
|---|---|---|
| `created` | the object appears | once per object while the controller runs (repeated only while it returns an error); objects that already exist when the controller starts are **not** `created`, only `sync` |
| `updated` | the object changes (spec, labels or annotations; status-only changes are ignored) | not replayed after downtime |
| `deleted` | the object is being deleted | always runs, even after downtime (finalizer, see below) |
| `sync` | on start for every existing object, on every create/update, on a periodic resync and on a change to an owned object | level-based: the function makes the world match the object, every time |

The event-style dev writes `created`/`updated`/`deleted`; the state-style dev
writes only `sync`; both may be mixed on the same type. `sync` is never
called for an object being deleted: that is `deleted`'s job.

`owns` works through owner references: the handler marks what it creates
with `controller.Own(owner, obj)`, a helper of the door package, so the dev
never calls controller-runtime for it.

### New types: `@CRD`

```go
package database

// Database is a database the controller provisions.
// @CRD(group=acme.io, version=v1, scope=Namespaced)
type Database struct {
	metav1.TypeMeta   `json:",inline"`
	metav1.ObjectMeta `json:"metadata,omitempty"`

	Spec   Spec   `json:"spec,omitempty"`
	Status Status `json:"status,omitempty"`
}
```

| Key | Required | Meaning |
|---|---|---|
| `group` | yes | API group (`acme.io`) |
| `version` | yes | API version (`v1`) |
| `scope` | no | `Namespaced` (default) or `Cluster` |
| `plural` | no | default the lowercased kind plus `s` |

From it `go generate` writes:

- the CRD YAML (OpenAPI schema from the struct and its `json` tags; a
  `Status` field turns on the status subresource);
- the `DeepCopy` methods and the scheme registration the controller needs;
- the `Database` list type.

## Behaviour

- One controller-runtime manager per app, built by a new factory
  (`factory/contrib/sigs.k8s.io/controller-runtime/v0`) from the existing
  client-go config (`boost.factory.k8s.*`: kubeconfig or in-cluster).
- The door provides the manager's `client.Client` to the graph, so a
  handler's constructor receives it to read and write the cluster.
- One controller per watched type, carrying all the `@Controller` functions
  of that type.
- `deleted`: when a type has an `on=deleted` function, the controller adds a
  finalizer to its objects and removes it after the function returns nil, so
  deletion waits for the function.
- Leader election on by default, so several replicas can run and only one
  reacts.
- The manager's health and readiness probes and metrics are served by the
  manager, configured under the factory.
- RBAC: `go generate` writes a ClusterRole per app with the verbs the door
  needs on each watched and owned type (get, list, watch; update and patch
  for the finalizer; events and leases for leader election). Owned types
  also get create and delete. The binding to a service account belongs to
  the deploy (non-goal), so it is not generated.

### Config

Under the new factory root (`boost.factory.controllerruntime.*`):

| Key | Default | Meaning |
|---|---|---|
| `namespace` | `""` (all) | namespace watched |
| `resync` | `10h` | period of the `sync` resync |
| `leaderElection.enabled` | `true` | |
| `leaderElection.id` | the app name | lease name |
| `health.addr` | `:8081` | probes |
| `metrics.addr` | `:8082` | metrics (`:8080` is echo's default port) |

### Generated files

```
gen/builder/<app>/controller_module.go     # manager, one controller per type, the handlers
deploy/crd/<group>_<plural>.yaml           # one per @CRD
deploy/rbac/<app>.yaml                     # ClusterRole of the app
<package of the @CRD type>/zz_generated.boost.go # DeepCopy, list type, scheme registration
```

`deploy/` is configurable (`boost.builder.deploy`).

## Validation (generation fails, nothing written)

- `on` missing or unknown; `owns` without `on=sync`;
- handler signature other than `func(context.Context, *T) error`;
- `T` neither a `k8s.io/api` type nor a `@CRD` type;
- two functions with the same `on` for the same type in one app;
- `selector` that does not parse as a label selector;
- `@CRD` without `group` or `version`, an unknown `scope`, or a struct
  without `TypeMeta`/`ObjectMeta`;
- a type watched in two apps with `on=deleted` in both (two finalizers
  fighting);
- the rules every door shares (app name, unexported handler, package `main`,
  method without provided receiver).

## Non-goals

- Admission and conversion webhooks; several versions of one CRD.
- Generating the Deployment/Helm chart of the controller.
- Several clusters per app.
- A dev-facing reconcile API (requeue-after, result types): the function
  returns an error or nil.

## Anti-goals

- The dev touching controller-runtime concepts (manager, `reconcile.Request`,
  predicates, finalizers, work queue).
- The dev writing CRD or RBAC YAML by hand.
- Instantiating controller-runtime outside the new factory (Iron Law 4).

## Left to the builder

My calls (Claude), open to change:

- controller-runtime as the engine; the factory reuses the client-go config.
- The kind comes from the handler's parameter type, not from a key.
- `deleted` backed by a finalizer (guaranteed), at the cost that uninstalling
  the controller leaves objects stuck in deletion until the finalizer is
  removed by hand.
- `created`/`updated` are best effort after downtime; `sync` is the safety
  net.
- `owns` and `selector` exist from the first version, because the example
  that motivated the design is "a Deployment with a label gets a Service".
- `zz_generated.boost.go` is written next to the `@CRD` struct, not under
  `gen/`: Go requires `DeepCopy` in the type's package.
- Default `app=api` like the other doors.

Also left: how the event kind travels through the work queue
(controller-runtime typed requests), the library used to build the CRD schema
(`sigs.k8s.io/controller-tools` or own code), and the test shape (fake
client for the handlers, envtest for the e2e of the example). The example
(`builder/examples/simple`) gains a `controller` app with the
"Deployment → Service" case, and `builder/README.md` gains the `@Controller`
and `@CRD` sections.
