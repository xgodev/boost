# inject

`inject` generates [fx](https://github.com/uber-go/fx) modules from comment
annotations. You annotate constructors with `@Provide` and entry points with
`@Invoke`; the generator reads them with the [`annotation`](../annotation)
package, builds the dependency graph, checks it and writes one fx module per
function plus a root `Module()` that wires the whole application.

## Annotations

| Annotation | On | Meaning |
|---|---|---|
| `@Provide(index=N)` | constructor | result `N` is provided to the graph |
| `@Provide(name=X, index=N)` | constructor | result `N` is provided as the named value `X` (`name:"X"`) |
| `@Provide(group=X, index=N)` | constructor | result `N` is added to the value group `X` (`group:"X"`) |
| `@Inject(index=N)` | `@Provide`/`@Invoke` function | parameter `N` must have a provider in the graph |
| `@Inject(name=X, index=N)` | `@Provide`/`@Invoke` function | parameter `N` receives the named value `X` |
| `@Inject(group=X, index=N)` | `@Provide`/`@Invoke` function | parameter `N` (a slice `[]T`) receives every `T` of group `X` |
| `@Invoke` | function | the function runs when the application starts (`fx.Invoke`) |

`index` is the zero-based position of the result or parameter and is always
required. A parameter without `@Inject` is linked to a default provider of
the same type when one is annotated; otherwise the application must provide
it (for example with `fx.Supply` or another fx module).

```go
package greeting

// NewGreeter greets informally.
// @Provide(index=0)
func NewGreeter() *Greeter { return &Greeter{Prefix: "Hello"} }

// NewFormalGreeter greets formally.
// @Provide(name=formal, index=0)
func NewFormalGreeter() (*Greeter, error) { return &Greeter{Prefix: "Good morning"}, nil }
```

```go
package app

// Announce runs on start.
// @Inject(name=formal, index=0)
// @Inject(group=names, index=2)
// @Invoke
func Announce(formal, casual *greeting.Greeter, names []string, board *Board) { ... }
```

## Generating

Add a `go:generate` line to the application and run `go generate`:

```go
//go:generate go run github.com/xgodev/boost/inject/cmd/inject --boost.inject.output=gen
```

```bash
go generate ./...
```

The command starts with `boost.Start()`, so its settings are boost config keys
(flags, env vars or config files):

| Key | Env | Default | Description |
|---|---|---|---|
| `boost.inject.path` | `BOOST_INJECT_PATH` | `.` | directory scanned for annotations |
| `boost.inject.output` | `BOOST_INJECT_OUTPUT` | `gen/inject` | directory that receives the generated modules; must be inside the Go module |
| `boost.inject.graphviz` | `BOOST_INJECT_GRAPHVIZ` | (empty) | optional file that receives the dependency graph in Graphviz DOT format |

The output mirrors the import path of each annotated function:

```
gen/
  module.go                                   # package gen: func Module() fx.Option
  github.com/acme/app/greeting/newgreeter_module.go
  github.com/acme/app/app/announce_module.go
```

Each `<func>_module.go` declares `<Func>Module()`, an `fx.Module` with the
modules it depends on and `fx.Provide`/`fx.Invoke` of the function, wrapped in
`fx.Annotate` with `fx.ParamTags`/`fx.ResultTags` when names or groups are
used. Every run rewrites the output and removes generated files (those
starting with `// Code generated by inject; DO NOT EDIT.`) that are no longer
produced; other files in the output directory are kept.

The application uses the root module:

```go
func main() {
	boost.Start()

	fx.New(gen.Module()).Run()
}
```

## Validation

The generator fails, without touching the output directory, when:

- `index` is missing, out of range or declared twice;
- a function has both `@Provide` and `@Invoke`, or `@Inject` without either;
- `@Provide` points to an `error` result, or uses both `name` and `group`;
- `@Inject(group=...)` is on a parameter that is not a slice;
- two functions provide the same value (same type and name; groups may have
  many providers);
- an `@Inject` parameter has no provider;
- the dependencies have a cycle, or a function depends on what it provides;
- an annotated function is unexported or in package `main` (the generated
  code must import it);
- the output directory is not inside the Go module.

Annotations on structs and methods are ignored with a warning.

## Library

The command is a thin wrapper over the package API, which can be used to
build other generators or to check that the generated code is up to date:

```go
modulePath, moduleDir, _ := inject.FindModule(".")
entries, _ := inject.CollectEntries(".")
g, _ := inject.NewGraphFromEntries(ctx, entries)
files, _ := inject.NewGenerator(g, inject.GeneratorOptions{
	ModulePath: modulePath,
	ModuleDir:  moduleDir,
	OutputDir:  outputDir, // absolute
}).Render(ctx) // or Generate(ctx) to write them
```

`WriteGraphviz`/`ExportInjectGraphToGraphviz` export the graph in DOT format.

Generators built on top of inject (such as [`builder`](../builder)) reuse:

| Function | Purpose |
|---|---|
| `GeneratorOptions.BaseImport()` | import path of the output dir |
| `ModuleOf(base, entry)` | import and module call (`gen_x_hash.NewXModule()`) of a component |
| `Provider(g, pkg, tp)` | component and result index providing the default value of a type |
| `Alias(prefix, name, path)` | collision-free import alias (`prefix_name_hash`) |
| `ExecuteTemplate(tmpl, name, data)` | executes a template and gofmt's the output |
| `WriteGenerated(ctx, dir, files, header)` | writes files and removes stale ones starting with `header` |

See [`examples/simple`](./examples/simple): its tests run the generated
application and fail when `gen/` is stale.

## Limitations

- Types are matched by package name and type expression, not by import path:
  two packages with the same name and type name are seen as the same type.
- Each generated `<Func>Module()` returns its options only on the first call
  (`sync.Once`), so a constructor reached by several modules is registered
  once. Build the fx application once per process.
- fx provides every non-error result of a constructor, whatever `@Provide`
  declares; `@Provide` only tells the generator which results to track.
- The scan also loads the packages imported by the scanned code, which makes
  a run take a few seconds on large dependency trees.
